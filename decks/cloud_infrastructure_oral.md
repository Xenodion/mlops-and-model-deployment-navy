# What does it take to follow a fleet of rides?

Team NAVY · Advanced Cloud AI Infrastructure · Working outline for the oral

The decision for the audience is where to train each model and where to serve their joint output. The sequence below could fit about ten minutes if the courses share an oral slot. That duration is a planning assumption for Cloud. The visual suggestions are alternatives the presenter can choose once the evidence is available.

| Slide | What the audience could learn | Possible evidence and why it helps |
|---|---|---|
| 1 · A ride in progress | Imagine a fleet operator reviewing a scooter ride. The five-class trajectory model updates its category as windows arrive. A separate detector estimates fall risk from the most recent ten seconds. After the ride, both outputs can be reviewed retrospectively. Fleet demand and operational usefulness are pilot assumptions. | A short ride timeline with two labelled traces could explain why an incoming window and an uploaded ride have different compute budgets. A cropped inter­face view could work equally well. |
| 2 · Where the compute happens today | Follow one sensor record through cleaning, the ride CNN and cumulative aggregation, fall features and scoring, then one API response. Follow training separately through GBG500 and SRV3490 to versioned artifacts. Distinguish local kind serving, the shared registry and temporary Vertex jobs. | A current-system diagram could use one ride and two return values. A photograph of the cluster dashboard adds less here than showing which operations share a process. Covers the current inventory requested in step 1. |
| 3 · What must fit on a worker? | Size each complete model, input volume, rides, readings, windows, tensor shape, serialized bytes and working memory. Compare host RAM with peak RSS, device capacity with peak allocated VRAM. Scikit-learn fitting and sensor preprocessing consume CPU even on a GPU worker. | A two-row sizing table could pair each model with its data and hardware. The fixed E3 golden input contains 1,885 windows of 6 × 300 float32 values from 100 rides. Use measured peaks from the release run when available. Addresses step 2. |
| 4 · What makes two runs comparable? | Identify the image digest, both registry versions, input hashes, runtime and machine. Separate job setup, cold first response and warmed requests. Alternate paired backend runs, synchronize CUDA, record batch, threads, concurrency, repetitions and run variation. | A workload card or a short experiment matrix could identify the single changed variable in each comparison. The historical T4 runs illustrate why recording actual CUDA use matters. Only one of the three used CUDA. |
| 5 · How many riders can one service follow? | Measure the complete live request with cumulative state and both predictions. Measure post-ride separately by length. For each load level report offered and completed requests/s, mean, p95, errors and peak RAM/VRAM. Relate live capacity to request cadence per rider. | Two latency-versus-load curves or a compact capacity table could show where p95 exceeds the proposed 200 ms live budget. Label observed concurrency, replica count and duration. The local b80aeeb replay proves functionality across 100 rides and 200 live windows. Capacity still needs a timed run. |
| 6 · Does one optimization earn its place? | Proposed hypothesis: ONNX Runtime FP32 improves E3 CPU inference throughput for larger batches while preserving predictions. Hold hardware, preprocessing, inputs and batch fixed. Check probability or class agreement, golden macro-F1, latency, throughput and memory. Verify whether any component gain survives the joint request path before recommending a serving change. | A before/after table could carry the raw values and per-batch speedup. A paired dot plot could reveal where the optimization loses. Step 4 rewards the comparison even if the original runtime wins. |
| 7 · Where should training run? | Time preparation, fitting and evaluation of E3 and fall risk separately. Compare equivalent E3 CPU and one-GPU training, with seed, effective batch, epochs, quality and data held fixed. For fall risk, time CPU feature extraction and logistic regression. Explain whether memory, training duration or synchronization makes DDP, FSDP or ZeRO worth investigating. | Stacked stage times and peak memory could support the decision. A matched one-versus-two GPU run becomes useful if training time warrants it. Artificial replication measures compute scaling and adds no independent examples. Step 5 accepts an evidence-based single-worker decision. |
| 8 · What should the fleet pay for? | Compare a shared dual-model CPU service with GPU hosting or separate model workers if bottlenecks warrant it. Include idle capacity, model duplication, network hops and batching delay. For each cost estimate state region, machine, price date, hours, request volume and utilization. Separate serving from intermittent training and Spot interruption costs. | A scenario table with monthly cost and cost per thousand completed requests could accompany a proposed architecture. Measured capacity anchors the denominator. Distinguish a proposed autoscaler from a replica count actually tested. |
| 9 · How would the service recover, and what comes next? | Explain readiness of both outputs, overload monitoring, loss of a replica, rollback of the image and paired model versions, then replay to verify recovery. Close with the evidence that would change the hosting decision and the owner of the next test. | A recovery timeline or a decision table could connect symptom, observation and action. Cite measured recovery only after a timed drill. Before a pilot, calibrate demand, alert usefulness and the post-ride budget. |
